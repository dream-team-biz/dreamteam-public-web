Anatomy of one task

In one real feature, AI agents built and checked the work, I made the calls that mattered, and the record shows what it took in time and money.

Alex Rapoport · October 2026

  • T-70718–19 September 2026
  • 20 h 25 minelapsed, first step to merge
  • 4 h 18 minwaiting for my decision
  • at least $163list API prices, not spend

Measured from the task's record and its session transcripts. List prices are Anthropic's published pay-per-token API rates. With no measured baseline for a person doing the same work, I make no comparison.

Tasks on our board, the list of every task we plan, often started too early and stopped halfway. The board didn't record what waited for what. In September, DreamTeam, our team of AI agents, built the first step of the fix in one task, T-707. Now a link between tasks can say what kind of wait it is, and why. Before any code, four agents reviewed the task in a 22-minute step for about $20 at list prices. They found a rule that could stop the whole board from loading.

I show a real task so you can judge the process by its record, kept in our private code repository. Excerpts from that record are verbatim; the “after” block is reflowed to fit, and my own words are lightly edited.

Constraints between our tasks went unrecorded

When we measured the board on 17 September 2026, 264 of 685 tasks recorded no dependency, and 47 stated an ordering only in text the board doesn't read. We found seven kinds of ordering constraint; only two fit “this task must follow that one”.1

My words that day:

“I don't run tasks in the order they were planned… I see a lot of tasks that stop in the middle and say: ah, actually I depend on another task. I need the mechanism from the other task. It's not built — what to do? … In the end I waste time and tokens…”

Alex, 17 September 2026, lightly edited. Tokens are the units AI models read, write and bill by.

That conversation was a brainstorm, DreamTeam's structured interview that turns an idea into a vision and a plan. Its plan was an epic, a larger goal split into nine tasks, with T-707 first.

Nine criteria told the agents when the task was done

Every agent works from the task's contract; its acceptance criteria say when the task is done. Here are T-707's nine, in plain words and in the agents' own text. The readiness review, four agents reading the contract before any code, and a decision of mine changed several and added the ninth.

Agents built and checked it; I made the calls

A task runs in four stages: Init gets it ready, Run builds it, Finalize checks it, and Close merges it, joining the change to our main code. I start each stage; Init stops at a gate, where the task waits for my decision. Inside most stages, the orchestrator, the agent that runs the task's steps, hands the work to agents with one role each.

Init: four agents read the contract before any code

In the readiness review, a reviewer, an architect, a tester and a backend developer read the contract. Two of them found that a link typed the natural way would be misread. The board is stored in YAML, and a loader for the older YAML 1.1 standard reads the bare word “on” as true:

What mattered is where it was caught: the design's own worked example. The loader the design planned to use would have misread it. The contract fixed the root cause with a YAML 1.2 loader, rather than the backend developer's workaround, “mandate the JSON form”. The review also caught a merge test that would pass without the new code, and a promised error code the task's files couldn't produce.

The backend developer, and separately the architect, found a bigger problem. Under the design I had approved, one row whose record and ID list disagreed would stop the whole board from loading. The architect proposed correcting the list on load instead; the contract added a logged warning.

At the gate, I approved that rule. The trade-off: failing closed, one stale row stops every reader and automated check; failing open, a row can be silently wrong. From the decision record:

“The duty is redistributed, not removed. With a normalizing V2 a stale record propagates silently — depends_on is rewritten from a dead id — instead of halting. …”

T-707's decision record, Consequences, 19 September 2026. V2 is the rule that keeps the ID list, depends_on, in step with the record. A stale record is out of date; a dead id is an ID that no longer exists.

So the duty passes to criteria 5 and 6. The correction on load only keeps the board loading; it can't tell that a record is stale. Renumbering a task rewrites every link to it. A merge where the two sides changed the ID list and the dependency record differently goes to a person, and nothing is written. I kept the task whole for a related reason: those two had to come before the nine live records. It was a judgment call: the reviewer would have split off the spreadsheet criterion; the backend developer argued against.

Run: one agent built it; others reviewed, tested and documented it

A developer agent built criteria 1 to 8 in three parts, tests included. Then an architect updated the design documents to match my decision, so they describe what shipped.

A reviewer checked the code: a separate agent on the same model as the developer, without the developer's conversation. It has no editing tools but can run commands. It approved with one real finding: in a command the tool prints for a person to run, an apostrophe in a reason ended the shell's quoting early. Criterion 3 had called that command safe; the readiness review missed it. The reviewer reproduced it (“the safety claim is wrong”). The developer's fix quotes the record for the shell. A test that failed first, then passed, parses the printed command back into the same record.

A tester ran the 378 tests selected for this change: 375 passed, 3 skipped as before because of the environment. The full run passed 15,680 tests and failed none (75 skipped; local end-to-end tests are left out), so the existing tests that ran still pass. The tester checked all nine criteria against the code, not the developer's report.

A design review sent the architect's update back once, then approved it, and a technical writer documented the change.

Finalize and Close: a last check, my approval, the merge

A tester's last review recommended going ahead. The orchestrator replayed the demo, checking each command for an expected string or exit code, the number a program ends with; every command passed.

I approved the result by starting the close, based on the run report, the review findings and the demo replay, not the diff (the line-by-line change). At close I rely on the independent review, the tests and the merge queue; my calls are at the gate. A person closes every task; code reaches our main branch through GitHub's merge queue, which runs automated checks first.

Dependencies now have a schema: every link in a dependency record carries a kind and a reason

Closing T-707 unblocked T-699, T-700 and T-701; as of 4 October 2026, six of the eight after it are done. Of the seven kinds of constraint, two stay out of scope by design, and T-705 reports a third.1 We haven't yet measured whether fewer tasks stall.

20 h 25 min elapsed, and at least $163 at list API prices

The task took 16 agent runs in 4 sessions (one per stage). My part was six messages: the four commands that started the stages and two answers before Run. Reading and deciding took me one to two hours, by my estimate. The task waited 4 h 18 min for my decision at the gate.

About $5 at most is T-707's share of what we actually paid for our subscription in September. T-707 ran on one seat, one user's license, of our Team plan. A week of that seat costs about $28.85. T-707 was 16.5% of the seat's recorded work that week: $4.75.3

Neither figure includes people's time, the brainstorm that planned the work, or building DreamTeam itself. $163 is what the work would cost at pay-per-use prices; $5 is T-707's share of a flat subscription, a monthly price for a weekly usage allowance.

One task is an example, not a benchmark

I chose T-707 from a shortlist of ten feature tasks. It built something new, and its run had no unexpected failure. Its record has a token row for every agent run except the readiness review's four (the rows undercount output; see note 2). A run that went wrong would make a different note.

The run's verdict was “Complete-with-follow-ups”, none blocking. Three of its five follow-ups:

  • A board check catches a record and its ID list drifting apart, but its message doesn't say so.
  • The architect deferred a board-wide rule (“always error”) rather than invent it here; a later task has reshaped it.
  • The task's own board row still shows its criteria as worded before Init.

This is DreamTeam building itself, which it does almost every day; there is no outside case to show yet. Making it work inside anyone's repository is what we are building now.   1. The seven kinds of ordering constraint, from the brainstorm's research:
    1. build order: a task needs a mechanism another task builds;
    2. needs output: a task needs a file or result another task produces;
    3. would collide: two tasks change the same files, with no order between them;
    4. ordering between one task's own criteria;
    5. work that must land in a single commit, one saved change to the code;
    6. a need that no task provides;
    7. an agreement (an interface, file or value) that no one defined before the code was written.
    Only the first two fit “this task must follow that one”. The dependency record covers the first three; the fourth and fifth are out of scope by design; T-705 reports the sixth; the seventh fits a link only in part. ↩
  2. The $163 is a lower bound, priced from the token counts in T-707's record. The readiness review left none there; its cost, $19.72, was recovered from the session transcript. The record leaves out some orchestrator calls and undercounts the agents' output. Every write to the cache is priced at Anthropic's cheaper rate, the one for a cache kept five minutes. Not reconciled with any invoice. ↩
  3. The $5: a seat on our Team plan costs $125 a month, so a week is $125 × 12 ÷ 52 ≈ $28.85. Claude Code is the tool our agents run in. I took T-707's share of everything the seat did in Claude Code from 14 to 21 September, weighting each call by its list price. Both sides of that share come from the seat's session transcripts, not from the $163. It is an upper bound: any use of the seat outside those transcripts would lower it. ↩
