A wait

A task's start stops while any task it waits for is not done

Each wait is a record: the task, its kind, build order or needs an output, and a one-sentence reason.

A collision, two tasks that would clash if run together, is the third kind, and it orders nothing. It is declared once and checked at the start against tasks already running; what the check knows it cannot read, it reports instead of clearing.

You decide

If a task it would collide with is already running, the start puts that to you.

The order

The order is worked out from the records, not typed by hand

The list a task waits on comes from its record, collisions left out. An import, which loads new tasks onto the board, ignores a typed list beside it.

The epic's last task

The last task of the epic waits for every task, and closing the epic begins there

It carries a build-order wait on every other task, written when the plan became tasks. When the last of them closes, it is free to start: how the epic closes.

The small print

The collision check's limits, as DreamTeam states them

A partner counts as already running when its own branch copy says it has started. The check reads the remote branches as last fetched, with no network, so it is only as fresh as that fetch; its soundness is “evidence, not a proof”.

A named need

A task may also name what it needs and be matched to the task that provides it.

Where “ready” is not checked

The check on setting a task to ready covers that one command: an import can still write “ready” without it.
