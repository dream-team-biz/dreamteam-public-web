The method

A DreamTeam brainstorm is the planning session

  1. S1Vision, you approve
  2. S2Design, you approve

S1 · Vision

DreamTeam interviews you hard on eight dimensions and quotes your answers

  • What it buys: a plan built on what you require.Elaborate

    Each stage's file is committed as soon as it is written, so a fresh session resumes from the files.

    The vision leaves out data fields, module names, command contracts, algorithms, task lists and library choices: they are the design's job. A requirement is proven wrong by a person, not by the repository.

    Leaving S1 early takes an explicit override, and its reason is recorded.

    On record: in BS-117, dimension 7, Partial: “Not probed. … file scope and executor assignment are S2 and S3 output, which the rubric excludes from a vision.” The executor is the agent role that will do a task.

The grilling: DreamTeam interviews you on each dimension, in rounds, and looks the facts up in your code itself. It goes on until it can state that the whole task set could be written from the vision.

The eight are tuned to DreamTeam: one person decides, and tasks are scheduled by priority and readiness, not by date. So there is no stakeholder or timeline dimension; who does the work is asked instead.

The vision states the goal, the requirements and the non-goals. It holds no design: “orders are kept in one database table” could only be proven wrong by reading the code, so it moves to S2.

S2 · Design

Every requirement is traced to a component or contract

  • What it buys: the design is decided once, while changing it is cheap.Elaborate

    Each contract is numbered, so the plan and the reviewers can cite it on its own.

    The low-level design adds exact data shapes, command contracts, algorithms and the file plan; where the two differ, the high level governs.

    Rejected alternatives are named, each with the reason it was rejected.

    On record: in BS-117, the engineer took the low-level design DreamTeam offered, choosing its recommended option, “Yes, write the LLD”.

The high-level design (HLD) maps every requirement to a named component or a contract: a numbered piece of the design that tasks build on.

The low-level design (LLD), offered at this stage, fixes the exact shapes. HLD and LLD are software design's standard stages; DreamTeam develops both with you, and you approve each.

Back to the six stages

S3 · Draft plan

The design is broken into tasks, each with its role, files, criteria and confidence

  • What it buys: each task arrives with its conditions of done already written.Elaborate

    Ids are local to the plan; real task ids come when the tasks are created.

    A task with no dependency says why, in one sentence. An order stated only in a sentence, not as a link, makes the draft incomplete.

The draft plan breaks the design into tasks like those above. Acceptance criteria are the conditions of done, written to be copied word for word into the task.

Then its dependencies, each a typed link with a one-sentence reason: build order, needs an output, or would collide. Waves, tasks that can start at the same point, are derived from the links.

This draft is what the panel reads next.

Back to the six stages

S4 · Panel

At least two reviewer agents check the plan, and every finding gets a decision

  • What it buys: a defect is found in the plan, not in the code.Elaborate

    A finding is a problem a reviewer agent reports; a blocker is one that must be resolved — built into the plan, or deferred only with your sign-off.

    The reviewer has no editing tools, and may not defer to another agent's verdict. A specialist such as DevOps may run on a cheaper model.

    On record: in BS-117, the engineer's decisions came as a table, each with a recommendation.

One more check: until now the orchestrator, the agent running the brainstorm, wrote alone. Now at least two reviewer agents read the draft, each asked to report, not to edit.

The reviewer and the architect run on the strongest model. In BS-117 the reviewer agents ran in parallel.

Back to the six stages

S5 · Plan

You approve the plan — all at once or task by task — before any task is created

  • What it buys: one decision, made once, with every task in view.Elaborate

    Confidence comes in four named tiers, from High — a well-understood pattern, clear files, no open unknowns — to Low, which is escalated before the task is created.

    On record: in BS-117, the design's approval reads v1.2: v1 at S2, then the amendments the panel brought.

The compiled plan is the draft plus every panel decision, with what changed since the draft; each task appears as a full card, criteria word for word.

An approved stage can still be amended: its approval gets a new version that says what changed.

Back to the six stages

S6 · Materialize

Before any task is written, a script reads the approval line in each stage file

  • What it buys: tasks that say exactly what was approved.Elaborate

    The check finds that an approval line is there, not who wrote it, so your yes is asked at every stage.

    The other stage gates are the agent's instructions, and you are present for each; the check in code stands where a miss would cost most.

The check in code is not the agent's judgment: the orchestrator runs it as the step's first instruction, and nothing else forces it.

Then materialize: the plan is copied, not rewritten, into the task registry, the file that lists every task. The registry is checked before it is committed; from then on, the tasks can be started.

What it leaves

After the brainstorm, the tasks are ready to run

The tasks are on the board, wave by wave; the first wave has nothing to wait for.

From here each task runs on its own: when it starts, it gets its own readiness check and your yes.

The cost: each stage takes a conversation, and the panel takes agent time; it pays off where rework costs more.
