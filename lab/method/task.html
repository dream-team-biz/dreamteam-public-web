The Dream Team Life Cycle

One task, from init to close

Each agent gets its part of the contract — for the developer, the whole contract, once — and you start every stage.

You are the engineer in control; the contract is the brief every agent works from, not a legal one.

Init

Init turns the contract into one decision, and nothing is built before your reply

Init completes the contract and has the agents its files call for review it, the alignment review; then it lays one packet before you. It writes planning files, not code.

The contract holds what the task is, what done means, and which files each agent owns

The contract is born with the task, its criteria copied word for word, and completed at init.

The agents the files call for review it apart, and meet only in your packet

The agents are picked by the files the task touches: the reviewer always, the architect when the change is structural, the tester and the developers by file type; none sees another's findings.

Each answers ready, concerns or blocked, with a confidence. The orchestrator, the main agent that runs the others, adds a three-line synthesis, and you get one packet: everything you need to decide, laid before you.

Readiness is how ready the task is to start, read in nine parts before any code.

You answer in words, and “yes” is not an answer

Your reply, in words, is the one decision on the task's content at init: proceed, proceed with another demo, reject part, skip the demo, enrich or stop. Then you start the run.

You decide

“Yes”, “ok” and silence are not an answer, by the orchestrator's instruction.

Run

Run: the orchestrator hands each agent its part, and a failure stops it for you

Each agent starts fresh with what its step needs, though it may read more: a short session, a separate view of the same job.

You decide

Nothing, unless it stops: then you choose to fix and rerun, re-plan or stop. When it passes, you start finalize.

On this page

Finalize

Finalize: a last review, the local gate and the demo, and every follow-up ruled

It starts only after a passing test. One tester gives a last review of what the change touched; the local gate, automatic checks run on the code in the task's own workspace, must then pass. The demo you chose, a scripted run that shows the change working, is replayed by default.

The closure notes say what was delivered, the files and the decisions. Each follow-up, work left for later, is filed as a task, marked not filed with a reason, or left for you. The task waits as pending, for your approval.

You decide

You read the closure notes, rule on each follow-up left for you, and start the close.

On this page

Close

Close: the merge, a check on the merged code, and the record kept

By the orchestrator's instruction, the close runs only after your approval. On GitHub it merges through a pull request once its checks pass.

Where a merge queue, a line of changes waiting to merge, is active, the merge goes through it; the queue checks each change again with those queued ahead of it.

A task on an epic's long branch, which stays open until the epic's last task lands it, merges straight into that branch.

A check refuses a follow-up still left for you. On GitHub, a check on the merged commit then comes before done; an optional mode only warns. Then the record is compiled and the workspace removed.

You decide

Starting the close is your approval; if the check on the merged code fails, the task goes back to pending and waits for you.

The small print

The files behind each stage

DreamTeam at commit 6b947dfb1:

  • the start, run, finalize and close commands, .claude/commands/dt-task-init.md, dt-task-run.md, dt-task-finalize.md, dt-task-close.md;
  • the pipeline definition, config/workflows.yaml;
  • the role charter, docs/system/ROLE_CHARTER.md;
  • the agents, .claude/agents/;
  • the task schema, shared/models/task_schema.py.
The file names, by group
  • The contract: one Markdown file, the brief given to the agents that do the work; its file name is internal and is not shown on this page.
  • The runlog: runlog.md — the step-by-step record; the orchestrator, not the agents it dispatches, writes the rows, and a resumed run reads it to skip the steps already done.
  • The stage records:
    • approval-findings.json — the alignment review: which agents it convened, and each one's verdict and findings;
    • dispatch-findings.json — the dispatch card: who runs the task, which agents, which branch;
    • result-findings.json — the result card: files changed, tests, key decisions.
  • Time and tokens:
    • rollup.json — the time-and-tokens summary, drawn from the step timings and the session transcripts; written as soon as each alignment-review round ends, so a start abandoned after that still leaves it in the task's folder;
    • timing_tokens.csv — the tokens each step actually used, by kind (fresh input, cache read, cache write, output), each with its source.
  • The demo, in showcase/:
    • consent.json — your decision on the demo, the scenario you chose, its fingerprint and when it was recorded;
    • resolved-commands.json — each demo step's command and the check that judges it, to read before anything runs;
    • playback.json — the replay, step by step: each command, its exit code, an excerpt of its output and whether its check passed; written on a pass and on a fail;
    • transcript.html — the same replay as a page you can read, each step marked pass, fail or not run.
  • The reports:
    • report-star-narrative.jsonl — the task's narrative, opened at the start and added to as the task runs;
    • finalize-report-….html — as configured today, the status dashboard focused on this task; named with the day's date, so a run on a later day keeps the earlier day's report;
    • reports/close-receipt-….html — the close receipt: the pull request, the merged commit, the required checks' results, the files and lines changed, and the tasks it unblocked;
    • squash-trace.json — the merge's audit, recorded before the merge: the task's commits, which the merge folds into one, and the message built from its runlog; the merged commit is added after.
The agents at init

At most three agents are convened, four when the architect is called.

The run's short forms

A design-only task stops after its design and its review; a documentation-only task is reviewed and documented.

The local gate

Five checks, in order: format, lint, a check that the files shipped into a customer's project match their source, type check, the selected tests; a failure stops finalize before the closure notes.

The lock and the resume

The task's status is written on its own branch, and pushing that branch is the lock: the main branch keeps the task ready until the close. Before it creates its branch, and again just before it pushes, the start looks for a remote branch with the task's id and stops if it finds one. The name comes from the title, so two starts collide. It is the start command's check, and a short race remains. A resumed run reads the runlog and skips the steps already done. The contract and the runlog should let a stranger resume the task.

The readiness table

In the packet itself the nine parts come in this order: quality, ROI, urgency, priority, rank, maturity, risk, dependencies, effort.
