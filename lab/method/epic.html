In DreamTeam's brainstorm · the copied documents

> Promoted from …
@ <sha> (<BS_ID>
materialization, <date>).

The line DreamTeam writes on top of every document it copies from the brainstorm into the epic, in the form its pipeline gives, cut with "…" where it names the document's file in the brainstorm. In it, <sha> is the commit, <BS_ID> the brainstorm and <date> the day. “Materialization” is DreamTeam's step that writes the epic from the approved plan.

Where it starts

A brainstorm starts the epic: its documents, its goal and its criteria

An epic comes from the full brainstorm, by copying, not writing: no agent is dispatched.

Its vision, its design (how the parts fit), its plan and its panel review (a panel's verdicts and findings) go into the epic's own folder. Each is marked with where it came from, and the detailed design goes too when one was made; the brainstorm's own files stay as the record.

You decide

You approve the plan; until you do, no task and no epic is written.

How it runs

It keeps its own order and stops for you at every task

What moves by itself: the order, set by the tasks' dependencies; its status, up to closing, except on a long branch, a branch of its own that stays open while the epic's tasks land on it, until its last task lands it. After each close, a scan lists the tasks now free to start.

You decide

At each task, you reply at its start and start its run, its finalize and its close.

Main or long branch

It runs on the main branch, or on its own long branch when all three conditions hold

The main branch, the shared copy of the code, is the default.

Closing the epic

Closing the epic: a reader who did not write the evidence grades each criterion, and you confirm

The last task of the epic, which closes it, is free to start once the other tasks close. Besides the grades, it writes the showcase, passes over the documentation and lands a long branch.

Done is written by a person, by the methodology's rule: code cannot check who asks.

You decide

You sign off what is left over, answer the release question (whether to make a release now) and give the verdict.

On this page

The end

The epic ends with one showcase and a record you can open

At the close an agent writes one showcase, a page that presents the finished epic: no program computes its numbers, and each number has a source.

When you confirm, the epic and its last task are done.

What a long branch costs, in full

Four shared files — the board, the decision log, the history and the changelog — never change on the branch: “a hard structural rule, not a social convention”. A task's status reaches the main board at the task's close, in its own write; until then it lives on the task's branch, and the main branch receives only each task's pending (awaiting your approval) and done. A later change on the main board never reaches the branch's copy. A task started on the branch reads the status of what it waits for from the branch's own copy of the board. The epic's moves to active and closing come only with a task's move to in progress. On a long branch that move is written only in the task branch's copy of the board, which never lands, so the main board's epic does not move by itself. Code and config files both sides changed are left for a person, and the freshness check, which stops a new task from joining a branch that has fallen behind, still calls the branch “fresh”; some document files are merged by a stated rule. A task's target is fixed when the task is locked. No epic branches from another epic.

Closing the epic, in DreamTeam's numbering

1 the evidence for each criterion, with the ledger of what is left over; 2 one showcase, written by an agent; 3 a documentation pass; 4 integration: nothing on the main branch, one promotion for a long branch; 5 the release question, asked before the showcase; 6 your verdict: the last task and the epic, done.

Its waits

The last task of the epic waits for every task through records written with the plan; its start stops while any is open, and a check warns if a task is left out of its waits.

Who reads the evidence

In a recorded close, a fresh reviewer with no part in the epic's tasks graded every criterion at one pinned commit, and the orchestrator only copied its grades. Nothing mechanical stops a false tick in the evidence.

A task deferred or added late

A deferred task blocks the close; a task added while closing sends the last task back to you, by a check that over-reports by design: a false alarm costs you a glance, a miss would cost an unchecked done.

How we checked

No measured number on this page: counts, durations and costs are in the worked examples. Every excerpt is word for word, cut only with “…”. A figure tagged “Schematic” is invented. “Story” is our word for the epic, not DreamTeam's: its model keeps “story” for a tier below the epic.
