Anatomy of one task

One real task, from plan to merge. Our tasks kept stalling halfway on work another task hadn't built yet, so T-707 gave our task board a dependency record: each link now has a kind and a reason.

Lab note · Alex Rapoport, founder of DreamTeam Lab · October 2026

01 · The first records

Its first records mapped the nine tasks of its own epic

T-707 wrote the dependency records for the nine tasks planned with it: 20 connections between those tasks, each now with a kind and a reason.

02 · Acceptance criteria

Nine acceptance criteria: the definition of done

  1. AC-1 Define the record: the task it waits for, the kind of wait, and why.
  2. AC-2 Keep the old ID list in step with it, never stopping the board from loading.
  3. AC-3 Let people type a record the natural way with the usual edit command.
  4. AC-4 Carry it through spreadsheet import and export.
  5. AC-5 Update every link when a task is renumbered.
  6. AC-6 The tool that suggests fixes adds to a record, never overwrites it; a merge of parallel edits flags a clash.
  7. AC-7 Give the epic's nine tasks real records, once AC-5 and AC-6 are in place.
  8. AC-8 Test every rule both ways, on copies of the board.
  9. AC-9 Update the design documents to match AC-2.

03 · The stages

Agents did the work in four stages; I decided at three points

  1. Init

    The alignment review: four agents read the task's contract before any code, and the contract was fixed.

    Caught: in the design I had approved, a link typed the natural way would have been misread.

    Engineer: approved the fixed contract

  2. Run

    Caught: the reviewer proved one of the contract's claims wrong; the fix came with a test that failed first.

    Engineer: started Finalize

  3. Finalize

    A last review, and a replay of the task's demo: every command passed.

    Engineer: approved the result, started the close

  4. Close

    GitHub checked the change again, automatically, on top of the latest code, then merged it.

Engineer: my decisions. In Run, review and fix repeat on their own, at most twice; a review still failing, or a failing test, stops the run for the engineer. How control works: The Life Cycle.

What every link in a dependency record carries

A schema is the fixed shape every record must have; each dependency record is validated against it.

on
The task it waits for, by ID, such as T-703
kind
One of three kinds:
  • build order: runs after the other task
  • needs output (artifact): uses something the other task produces
  • would collide (conflict): must not run at the same time
why
The reason, in words: never blank, 200 characters at most

Three states. A task has no record yet, or an explicit “no dependency” (none: true) with a reason, or one or more links. It can't go back to no record. T-707's own record is the second kind: “first task of the epic; it creates the record every other card declares against” (a card is a task contract).

Derived, not typed. The old ID list is rebuilt from the links, sorted and without the collide links, so every tool that reads it works unchanged.

Rejected: an unknown kind, a blank or over-long reason, a malformed task ID, the same task and kind twice, a link to the task itself, an unknown field.

Warn now, refuse later. Each load of the board warns once with the number of open tasks that have no record. T-704, not done as of 4 October 2026, is planned to make the board refuse new tasks without one. T-703 has already filled in records for 72 open tasks (one new row was left out).

Notes on the numbers, and the sources
  1. Before T-707, on 17 September 2026, 264 of 685 tasks on our board recorded no dependency, and 47 stated an ordering only in text the board doesn't read. The brainstorm behind the epic found seven kinds of ordering constraint:
    1. build order: a task needs a mechanism another task builds;
    2. needs output: a task needs a file or result another task produces;
    3. would collide: two tasks change the same files, with no order between them;
    4. ordering between one task's own criteria;
    5. work that must land in a single commit, one saved change to the code;
    6. a need that no task provides;
    7. an agreement (an interface, file or value) that no one defined before the code was written.
    Only the first two fit “this task must follow that one”. The dependency record covers the first three; the fourth and fifth are out of scope by design; T-705 reports the sixth; the seventh fits a link only in part.
  2. The $163 is a lower bound, priced from the token counts in T-707's record at DreamTeam's rate table v2.3 (read 4 October 2026; last refreshed against Anthropic's pricing page on 29 September). The alignment review left no token rows; its cost, $19.72, was recovered from the session transcript. The record leaves out some orchestrator calls and undercounts the agents' output; every write to the cache is priced at the five-minute rate. Not reconciled with any invoice. Neither price includes people's time, the brainstorm that planned the work, or building DreamTeam itself.
  3. The subscription's $5: T-707 ran on one seat of our Team plan; a seat costs $125 a month, so about $28.85 a week. T-707 was 16.5% of that seat's recorded work that week, $4.75: its share of everything the seat did in Claude Code, the tool our agents run in, from 14 to 21 September, each call weighted by its list price. Both sides of the share come from the seat's session transcripts, not from the $163. An upper bound: any use of the seat outside those transcripts would lower it. Per-step tokens and time: DreamTeam's tools/pipeline_timing.py and tools/telemetry_task_cost.py; the model for each step: .claude/commands/dt-task-run.md L23 and T-707's runlog L20.
  4. The task took 16 agent runs in 4 sessions, one per stage. My part was six messages: the four commands that started the stages and two answers before Run.
